# 서버 연결 상태 표시 회귀 검증

## 원인

기존 App은 첫 화면 로딩/수동 새로고침에서만 시스템 상태를 읽었다.
다른 화면의 요청이 실패해도 하단 상태는 갱신되지 않았다.
StatusBar는 서버 응답을 아직 받지 않은 상태에서도 오류 문자열이 없으면 연결됨으로 표시했고,
연결 오류가 나도 이전 app-info의 DB/문제 폴더 준비 상태를 계속 표시했다.

## 수정

- 공통 `useServerStatus` 훅으로 5초 간격 상태 확인, 요청별 3초 제한시간 적용.
- 초기 상태는 `서버 확인 중 / 데이터베이스 대기 중 / 문제 폴더 대기 중`.
- 연결 실패/응답 시간 초과/브라우저 offline이면 `서버 연결 끊김`과 빨간 점 표시.
- 이때 DB·문제 폴더는 과거 준비 여부와 무관하게 `대기 중`과 회색 점 표시.
- 새 상태 확인이 성공해야 `연결됨`과 각 자원의 실제 준비 상태를 표시한다.
- online, 창 복귀, 탭 복귀에도 재확인. 화면 리로드/초안 초기화는 하지 않는다.
- 브라우저가 인터넷 없음으로 보고하더라도 LAN 서버는 직접 재확인한다. 실제 서버 응답을 기준으로 판정한다.
- 상태 요청은 HTTP 캐시를 우회한다. 취소·제한시간 초과 이후의 늦은 응답은 무시한다.
- 동시 중복 확인을 막고, 컴포넌트 해제 시 요청·타이머·이벤트를 정리한다.
- 일반적인 활성 탭의 감지 시간은 최대 약 5~8초다. 브라우저 절전/백그라운드 타이머 제한은
  더 늦어질 수 있으며 복귀 시 즉시 재확인한다. 연결 복구 자체가 미저장 자료의 저장 성공을 뜻하지는 않는다.
- 백엔드 엔진, 계정·결선 저장 로직, 실제 사용자 DB 변경 없음.

## 검증

- 관련 테스트: `cd frontend; npm test -- src/tests/ServerStatus.test.tsx src/tests/App.test.tsx src/tests/Navigation.test.tsx`
  → 18개 통과. 초기/끊김/복구, 제한시간, 늦은 응답, offline/online, LAN 전용 접속, 중복 방지,
  수동 재시도, 해제 정리, 자원 준비 여부, 캐시 우회 검사 포함.
- 프런트엔드 전체: `npm test` → 18개 파일, 131개 통과.
- `npm run typecheck`, `npm run build` → 통과 (`dist` 직접 편집 없음).
- `python -X utf8 scripts/validate_problems.py` → 23개 정상, 오류/제외 0, 기존 경고 19개.
- `python -X utf8 -m pytest backend/tests -o addopts= -q --basetemp <임시 폴더>`
  → 602개 통과 (370.94초), 기존 Starlette/httpx 사용 중단 예고 경고 1개.
- `git diff --check` → 통과.

## 실제 프로그램 시험

기존 임시 검증 데이터로 별도 localhost:8024 서버를 켜고 회로도 분석 화면을 열었다.
연결됨/준비됨 확인 → 검증 서버 정상 종료 → 페이지를 유지한 상태에서 끊김/대기 중과
빨간/회색 표시 확인 → 같은 검증 서버 재시작 → 새로고침 없이 연결됨/준비됨 자동 복귀 확인.
회로도 화면은 유지됐다. 검증 탭을 닫고 검증 서버만 다시 정상 종료했다.
사용자가 운영 중인 LAN 서버와 저장 기록은 조작하지 않았다.
