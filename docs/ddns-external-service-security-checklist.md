# 보류 작업: ipTIME DDNS 외부 서비스 설정과 보안 점검

기록일: 2026-09-22

상태: 향후 작업용 체크리스트. 설정 완료 보고서나 즉시 실행 지시가 아니다. 사용자가 시작을 요청하기 전에는 공유기·서버·인증 정책을 변경하거나 외부에 공개하지 않는다.

## 1. 목표와 현재 확인한 상태

- 라즈베리파이 5 8GB, SSD 512GB, 정품 27W 전원, 액티브 쿨러, 집 유선 LAN을 사용한다.
- 당장은 도메인을 구매하지 않고 ipTIME A1004NS의 DDNS 주소를 사용한다. 원하는 이름의 등록 가능 여부는 아직 확인하지 않았다.
- 일반 사용자 약 20명: 비로그인 공용 포털에서 일정·시간표를 열람하고, 전기기능사 시뮬레이터는 개별 계정으로 사용한다.
- 관리자 본인: 본인 Android 휴대폰 앱에서 같은 DDNS를 통해 서버 상태와 하위 서비스를 관리한다. Android 사용은 2026-09-22 사용자 확인 사항이다. VPN을 필수 조건으로 확정하지 않는다.
- 개인 도구·파일은 본인만 접근한다. 마인크래프트 Java 서버는 추후 필요할 때 별도로 준비하며 이번 웹 공개에 포함하지 않는다.
- LAN에서 사용하던 계정과 기록은 함께 이전한다. 이전을 이유로 새 계정을 만들지 않는다.

사용자 제공 화면 기준이며, 실제 적용 직전에 다시 확인해야 한다.

| 항목 | 확인 내용 | 이후 처리 |
|---|---|---|
| 공유기 펌웨어 | 12.18.0, 화면에 최신 버전으로 표시 | 실행 시점의 업데이트·보안 공지 재확인 |
| WAN 주소 | 사용자가 제공한 앞자리 `211.245.`는 공인 IPv4 범위 | 실제 외부 주소 일치 및 외부 접속 가능 여부 별도 확인 |
| 인터넷 공유 기능 | 실행 | 유지 |
| 포트포워드 UPnP 릴레이 | 마지막 화면에서 중단 | 유지, 자동 개방에 의존하지 않음 |
| DMZ/Twin-IP | 사용하지 않음 | 유지 |
| 공유기 원격 관리 | 앞서 제공된 화면에서 비활성 | 외부로 열지 않음 |
| 포트포워드 | 앞서 사용자 정의 규칙 목록이 비어 있었음 | 전체 규칙·자동 매핑·IPv6 노출은 재확인 필요 |
| DDNS | 마지막 화면의 호스트 이름·사용자 ID가 비어 있음 | 아직 등록 완료로 간주하지 않음 |

인터넷 공유 기능은 집 안 기기가 인터넷을 함께 사용하는 기능이다. 서버 공개를 막겠다고 이것을 끄지 않는다. 공유기 원격 관리와 별도로 제작할 서버 관리 앱도 서로 다른 기능이다.

12.18.0에 A1004NS 대상 보안 패치가 포함된 것은 [공식 배포 공지](https://iptime.com/support/downloads/27033)로 확인했다. 이것이 모든 보안 문제가 해결되었다는 의미는 아니다.

## 2. 주소와 서비스 구성안 — 미구현

하나의 `선택한이름.iptime.org`에 HTTPS 입구를 두고 서비스별로 전달하는 안이다. 경로 이름은 예시이며 기존 프로그램에 이미 적용된 것이 아니다.

| 접속 경로 예시 | 서비스 | 접근 권한 |
|---|---|---|
| `/` | 공용 포털·일정·시간표 | 열람은 비로그인, 작성·수정은 관리자 |
| `/elec/` | 전기기능사 시뮬레이터 | 로그인한 사용자 자신의 기록만 |
| `/manage/` | 휴대폰 관리 앱이 사용하는 관리 화면/API | 본인 관리자 인증 + 추가 인증 |
| `/private/` | 개인 도구·파일 | 본인 전용 인증 |

- DDNS는 주소를 연결할 뿐, 암호화나 접근 제어를 대신하지 않는다.
- 경로가 다르거나 앱을 본인 휴대폰에만 설치했다고 접근이 제한되지는 않는다. 모든 관리 API에서 서버가 권한을 검사해야 한다.
- 같은 호스트의 여러 경로는 브라우저에서 같은 출처다. 쿠키 경로만 나누어 보안 격리라고 판단하지 않는다. 공용 페이지의 스크립트 취약점이 관리 기능에 미치는 영향까지 검수한다.
- 관리 서비스는 별도 프로세스·권한·인증으로 분리한다. 본인 휴대폰만 허용하려면 관리 경로에 클라이언트 인증서 또는 기기 결합 인증 같은 추가 장치를 검토한다. 구현·분실 복구 방법을 확인하기 전에는 관리 기능을 공개하지 않는다.
- `/elec/` 사용 시 라우팅, API 주소, 정적 이미지, 새로고침, 쿠키, 로그인 이동 및 기존 링크의 경로 호환성을 실제 테스트한다. 경로 접두사를 프록시에서 제거하는 것만으로 완료되었다고 보지 않는다.

### Android 관리자 앱 인증 권장안 — 미구현·세부 방식 미확정

- 앱 설치 파일은 본인에게만 배포한다. APK 비공개 배포 자체를 접근 제어로 간주하지 않으며, APK에 관리자 비밀번호나 공통 비밀키를 넣지 않는다.
- 최초 등록은 신뢰할 수 있는 서버 로컬 관리 화면/콘솔에서 시작한다. 짧은 유효기간의 일회용 QR과 명시적 승인으로 등록하며, 같은 Wi-Fi에 있다는 사실만으로 관리자 기기로 승인하지 않는다.
- 휴대폰에서 기기별 인증키를 생성하고 서버에는 공개키를 등록하는 방식을 검토한다. Android Keystore와 사용자 인증 연계를 사용하되, 기종·OS의 하드웨어 보안 지원 여부를 실제 확인한다. [Android 공식 문서](https://developer.android.com/privacy-and-security/keystore)
- 평소 사용 흐름은 앱 실행 → 지문 등 지원되는 잠금 인증 → 서버의 등록 기기 검증 → 관리 화면을 목표로 한다. 생체 정보 자체는 서버에 보내지 않는다.
- 화면 잠금만 추가하고 서버 인증을 생략하지 않는다. 검증된 인증 방식으로 재사용 공격 방지·세션 만료·API별 권한 검사·중요 작업 재인증을 구현하고 검수한다.
- 분실·교체·앱 재설치 시 기존 기기와 세션을 폐기하고 재등록하는 복구 절차를 마련한다. 기기 키나 관리자 자격을 앱 백업으로 무심코 복제하지 않는다.
- 등록 QR·복구 정보·APK 서명키는 비공개 보관한다. 앱 업데이트의 서명 유지와 설치 방법도 준비한다.
- 현재 확정된 것은 Android 사용뿐이다. 정확한 기종/OS, 잠금 인증 대체 수단, 최초 등록·복구 방법은 개발 시작 시 결정한다.

## 3. 설정·개발 순서

### A. 공개 전에 내부 환경에서 준비

- [ ] Git 상태와 기존 변경사항을 보존하고 현재 배포 버전·데이터 위치를 기록한다.
- [ ] 사용자 데이터와 설정을 백업하고, 새 폴더에 복원하여 같은 계정으로 로그인되는지 확인한다.
- [ ] 라즈베리파이용 64비트 OS·보안 업데이트·시간 동기화·ARM64 실행 환경을 준비한다. Windows 가상환경은 그대로 복사하지 않는다.
- [ ] 유선 LAN 주소를 공유기의 DHCP 예약으로 고정한다. 실제 빈 주소와 MAC을 확인하고 임의 주소를 지정하지 않는다.
- [ ] OS 계정과 서비스 실행 계정을 분리하고, 앱을 상시 root 권한으로 실행하지 않는다. 재부팅 후 자동 시작·정상 종료를 시험한다.
- [ ] 시뮬레이터 엔진이 메모리 세션을 사용하므로 기존 운영 문서의 worker 1개 조건을 재확인한다. 성능 개선을 위해 무작정 worker를 늘리지 않는다.
- [ ] 포털·시뮬레이터·관리·개인 파일 서비스가 서로 불필요한 데이터나 관리 권한을 갖지 않도록 분리한다.
- [ ] 서버 PC/라즈베리파이의 방화벽과 실제 수신 포트를 IPv4·IPv6 모두 확인한다. 컨테이너를 쓴다면 별도로 게시된 포트도 검사한다.

### B. 공유기 보안과 DDNS 준비

- [ ] 공유기 설정을 백업하고 관리자 비밀번호를 다른 서비스와 다르게 설정한다. 설정 백업도 비공개 보관한다.
- [ ] 인터넷 공유 기능 실행, UPnP 중단, DMZ/Twin-IP 미사용, 공유기 원격 관리 비활성을 재확인한다.
- [ ] 펌웨어 보안 업데이트를 확인하고, 필요한 업데이트는 중단 시간을 정한 뒤 적용한다.
- [ ] Wi-Fi 암호화·암호와 불필요한 WPS 사용 여부를 점검한다. 실제 지원 항목을 확인한다.
- [ ] DDNS 이름과 본인 이메일을 등록하고 정상 등록·주소 갱신을 확인한다. 이 이메일은 공유기 DDNS 등록용이지 시뮬레이터 가입 정보가 아니다.
- [ ] DDNS 조회 결과가 실제 WAN 주소와 일치하는지 확인한다. 상위 공유기·통신사 포트 차단 여부도 점검한다.

ipTIME은 공유기당 한 개 호스트 등록과 장기간 갱신되지 않은 호스트 삭제 정책을 안내한다. 세부 정책은 작업 시 [공식 DDNS 안내](https://www.iptime.com/support/faq/25913)를 다시 확인한다. 현재 12.x 화면은 [구형 펌웨어 안내](https://www.iptime.com/support/faq/24523)를 참고한다. 공유기 외부 관리 차단 등은 [공식 보안 설정 안내](https://www.iptime.com/support/faq/26459)를 참고한다.

### C. HTTPS 준비 후 필요한 포트만 개방

- [ ] Caddy 같은 리버스 프록시를 HTTPS 입구로 준비한다. 백엔드는 같은 호스트의 loopback 또는 외부에 게시하지 않은 내부 네트워크에서만 수신한다.
- [ ] 선택한 DDNS 호스트에 공개 신뢰 인증서를 발급할 수 있는지 실제 확인한다. DDNS 등록만으로 인증서가 생긴다고 가정하지 않는다.
- [ ] 서비스 접근 제어가 준비된 후 TCP 443을 라즈베리파이의 HTTPS 프록시에만 전달한다. 내부 8000번 HTTP 서버로 바로 전달하는 것은 HTTPS 설정이 아니다.
- [ ] 기본 운영안은 TCP 80도 프록시에만 전달하여 인증서 검증과 HTTPS 이동에 사용한다. HTTP에서 로그인·개인 데이터를 제공하지 않는다.
- [ ] 80번을 열지 않을 경우 443 TLS-ALPN 인증과 갱신이 실제 동작하도록 별도 구성·검증한다. 발급 때만 임시로 열었다가 갱신 경로를 막지 않는다.
- [ ] 인증서 데이터·키를 영속 저장하고 접근 권한, 자동 갱신, 실패 알림을 준비한다. 인증서 경고를 무시하도록 안내하지 않는다.
- [ ] 백엔드가 신뢰하는 프록시와 호스트 이름을 제한한다. 위조된 forwarded 헤더로 클라이언트 주소나 HTTPS 판정·접속 제한을 우회하지 못하는지 검사한다.

HTTPS 발급·갱신과 HTTP/TLS-ALPN 인증 조건은 [Caddy 공식 문서](https://caddyserver.com/docs/automatic-https)를 기준으로 검증한다.

| 외부 포트 | 계획 |
|---|---|
| TCP 443 | HTTPS 프록시로 전달 |
| TCP 80 | 위에서 정한 인증·HTTPS 이동 용도로만 사용 |
| 8000·8017·8023 등 앱 포트 | 외부에 직접 개방하지 않음 |
| SSH 22, 파일공유, DB, 관리 도구 자체 포트 | 외부에 직접 개방하지 않음 |
| 마인크래프트 포트 | 현재 개방하지 않음. 추후 별도 작업 |

포트 443만 열어도 그 뒤에 잘못 연결한 관리 기능은 노출된다. 포트 수가 적다는 이유만으로 안전하다고 판단하지 않는다.

### D. 계정·관리 기능·개인정보 보호

- [ ] 외부 관리자 접근에는 강한 고유 비밀번호와 MFA 또는 패스키 등 추가 인증을 준비한다. 휴대폰 분실 시 기기·세션 폐기와 복구 수단도 준비한다.
- [ ] 현재 가입/재설정 최소 6자 정책은 외부 공개 전에 사용자와 재검토한다. OWASP는 MFA 없는 비밀번호는 15자 이상, MFA 사용 시 8자 이상 기준을 제시한다. 지금 정책이나 기존 계정을 임의 변경하지 않는다.
- [ ] 비밀번호 해시 저장, 로그인 시도 제한, 계정 존재 정보 노출 최소화, 재설정 시 기존 세션 폐기, 중요 작업 재인증을 검수한다.
- [ ] HTTPS 환경의 Secure·HttpOnly·SameSite 쿠키, 세션 만료·로그아웃, CSRF 방어 및 CORS/출처 검사를 검증한다. 토큰을 주소·일반 로그에 남기지 않는다.
- [ ] 사용자 A가 사용자 B의 작업공간·JSON·분석 자료에 접근하지 못하고, 일반 사용자가 관리 API를 직접 호출해도 거부되는지 검사한다.
- [ ] 가입코드는 다시 넣지 않는다. 지인 가입 완료 후 신규 가입 닫기, 가입 시도 제한과 운영 인원 제한 방식을 검토한다.
- [ ] 공용 PC에는 관리자 비밀번호·인증키를 저장하지 않는다. 악성 프로그램이 있는 공용 PC의 안전을 웹 로그인만으로 보장할 수 없으므로 서버 전체 관리는 본인 기기에서 한다.

인증 정책의 근거는 [OWASP 인증 가이드](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)다. 위 항목은 이번에 구현하거나 통과 판정을 내린 것이 아니라 공개 전 확인 목록이다.

- [ ] `.env`, `user-data/`, 백업 ZIP, 로그, `.git`, 비공개 답안, TLS 키가 웹 파일로 제공되지 않도록 정적 파일 경로를 제한한다.
- [ ] 개인 파일 업로드는 크기·총용량·파일명·경로를 검증하고 실행 가능한 파일로 취급하지 않는다. 다운로드에도 본인 권한을 검사한다.
- [ ] 관리 앱은 온도·CPU·메모리·디스크·서비스 상태 조회부터 시작한다. 서비스 제어는 미리 허용한 대상/동작만 가능하도록 하고, 임의 셸 명령이나 Docker 소켓 전체 권한을 웹 앱에 주지 않는다.
- [ ] 서버 종료·삭제·복원은 추가 확인과 감사 기록을 남긴다. 서비스 삭제와 사용자 데이터 삭제를 별개로 취급한다.
- [ ] 서비스를 추가/삭제할 때 공개 경로·권한·데이터 위치·자원 제한·백업 대상·건강 점검·종료 절차를 함께 등록/해제한다.

## 4. 백업·운영·성능

- [ ] 프로그램 안의 `user-data/` 전체와 계정 ID 연결을 보존한다. 현재 데이터 백업에는 프로그램·운영 설정·TLS 인증서가 포함되지 않으므로 별도 보관한다.
- [ ] 기존 정상 종료/백업 도구를 활용한다. 실행 중 SQLite 파일을 탐색기로 단순 복사하는 방식으로 대체하지 않는다. Pi에서는 해당 환경의 정상 종료·백업 방법을 검증한다.
- [ ] 서버 SSD 외에 USB와 Google Drive 등 별도 위치에 암호화 사본을 보관한다. 암호키는 백업과 같은 곳에만 두지 않는다. Google Drive 업로드와 백업 암호화는 현재 구현 완료로 간주하지 않는다.
- [ ] 권장 시점은 사용일 종료 후 및 업데이트·이전 직전이다. 사용자의 계속 보관 선호를 반영하되 용량 경고를 두고, 자동 삭제는 별도 합의 없이 켜지 않는다.
- [ ] 백업 완료·실패를 표시하고 별도 새 폴더에 정기 복원 시험을 한다. 복사본이 있다는 것만으로 복구 가능하다고 판단하지 않는다.
- [ ] 서비스별 CPU·메모리·디스크 사용과 Pi 온도·저전압·디스크 부족, 로그인 실패, 인증서/백업 실패 알림을 준비한다. 로그 용량과 보관 기간도 제한한다.
- [ ] 외부 직접 공개는 집 공인 IP를 노출하며, 공유기/앱의 접속 제한만으로 회선 자체의 대량 트래픽 공격을 막을 수 없음을 전제로 한다. 이상 발생 시 포트 전달을 닫고 복구할 절차를 둔다.
- [ ] 외부 공개 전 [보류 중인 네트워크 최적화](network-optimization-backlog.md)를 별도 요청으로 진행한다. 사용자 데이터와 인증 응답을 공용 캐시에 저장하지 않는다.
- [ ] 약 20명 동시 로그인·결선 저장·동작시험 및 예상 7~8시간 사용 조건을 시험한다. 시뮬레이션 정확성과 계정 격리를 함께 확인한다.

기존 계정 이전·백업의 상세 절차는 [LAN 운영 안내](lan-classroom-service.md)를 참고하고, 실제 코드와 대상 환경에서 다시 검증한다.

## 5. 외부 공개 완료 판단 기준

아래를 통과하기 전에는 지인에게 주소를 배포하지 않는다. 테스트할 때도 필요한 경로만 제한적으로 연다.

- [ ] 휴대폰 Wi-Fi를 끈 LTE/5G에서 DDNS HTTPS로 접속되고 인증서 경고가 없다.
- [ ] HTTP 로그인은 제공되지 않고, 필요한 HTTP 요청은 HTTPS로 이동한다.
- [ ] 허용하지 않은 외부 포트와 관리·데이터 경로가 노출되지 않는다. IPv6도 따로 확인한다.
- [ ] 비로그인/일반 계정으로 개인 파일·타인 기록·관리 API에 접근할 수 없다. 본인 관리 기기의 추가 인증도 확인한다.
- [ ] LAN 기존 계정 로그인, 결선 저장·다시 열기, 분석 자료, 타이머·인터록 동작, 로그아웃이 정상이다.
- [ ] 서버 종료/재시작 시 연결 상태와 저장 실패가 정확히 표시되고, 저장된 데이터가 유지된다.
- [ ] 인증서 갱신 경로, 부팅 후 재시작, DDNS 갱신, 백업 복원을 검증했다.
- [ ] 전체 테스트·실제 브라우저 검사 결과와 남은 제한을 기록했다. 확인하지 못한 것은 미확인으로 남긴다.

## 6. 시작 전에 정할 정보

1. 사용할 DDNS 이름과 등록용 본인 이메일. 비밀번호·인증키를 문서나 대화에 적지 않는다.
2. Android 휴대폰의 기종·OS 버전, 관리 앱 형태와 기기 인증/분실 복구 방법. Android 사용 여부는 확인 완료.
3. Pi의 OS, 실제 저장장치 준비 상태, 예약할 내부 IP.
4. 포털·시뮬레이터 우선 공개 후 관리/개인 서비스를 붙일지 여부. 권장 순서는 공용 서비스 먼저, 관리 기능은 보안 검증 후다.
5. 외부용 비밀번호/MFA 정책과 기존 사용자 전환 방법, 신규 가입을 열어 둘 기간.
6. 백업 저장소·암호키 보관 장소·장애 알림 수신 방법.

## 재개할 때 사용할 요청

> ipTIME DDNS 외부 서비스 설정과 보안 작업 시작해줘. docs/ddns-external-service-security-checklist.md를 읽고 현재 상태부터 재확인해줘. 내부 검증과 백업을 먼저 하고, 외부 공개 직전에 실제 주소·포트·공개 범위를 확인받아 진행해줘.

이 문서 작성 시 공유기, 운영 서버, 프로그램 코드, 비밀번호 정책, 계정, 데이터, 포트, DDNS 설정은 변경하지 않았다.
